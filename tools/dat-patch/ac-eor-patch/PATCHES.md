## Usage

```sh
python3 patch_client.py list                 # the patch registry + provenance
python3 patch_client.py apply                 # orig -> patched (default paths), fixes PE checksum
python3 patch_client.py apply --only palette-leak,palette-leak-2 --no-checksum   # legacy byte-exact 2026-07-26 file
python3 patch_client.py apply --only palette-leak,palette-leak-2
python3 patch_client.py verify [file]         # report patch state + checksum (exit 1 on unknown bytes)
```

`apply` guards on input size (4,841,472 B) and pristine md5, so it refuses to
patch the wrong build; `--force` overrides for re-verifying an already-patched
input (which is a no-op on the code bytes — the patcher is idempotent).

## Doctrine (why this lane looks the way it does)

`acclient.c`, `acclient.map`, and the shipped `acclient.exe` are **three
different builds** whose offsets disagree (~0x60 apart in the DAT region; the
exe matches neither). So **every patch is located by a unique byte-signature**
(an invariant context window around the changed bytes), never by a quoted
address. A signature that is missing, or matches more than once, aborts the
patch. This is exactly how Mag's and Yonneh's community patchers work, and it
is the #1 guard against shipping a bad patch. (See
`docs/dat-patch/reports/client-headroom-dossier.md` §0/§8/§9.)

The signature is located by its **prefix + suffix** with the changed slice
masked, so the same site resolves whether the file is still orig or already
patched — that is what lets `verify` read a patched binary.

### PE checksum policy

The pristine exe's stored checksum (`0x004A60C3`) is correct and is how the
dossier confirmed the binary was unmodified retail. Any byte patch invalidates
it. `apply` **recomputes and writes the correct checksum by default** (the
proper on-disk artifact). AC's own client does not validate its exe checksum,
so this is cosmetic to the game but correct for any tool that does check.
`--no-checksum` leaves it stale to byte-reproduce the legacy file.

### `dat-decompress` — trevis's DAT zlib-decompression enable (SHIPPED 2026-08-16, SUPERSEDED 2026-08-17)

then rejects version-0 packs; NOPping that `je` lets decompressed records
proceed. Buys ~40–50 % on portal.dat texture bulk — the lever behind phase 2.

Graduated from candidate after the 2026-08-16 in-client gates. The 16:12 run

## `highres-force-mount` — always mount `client_highres.dat` (SHIPPED 2026-08-19; built 2026-08-18)

**Status: `enabled=False`.** Not in any shipped artifact. Flips to `True` only
after the box boot-mount verification below passes — that call belongs to the
orchestrator, not to whoever wrote the patch.

Owner-sanctioned mount mechanism per `docs/dat-patch/DECISIONS-2026-08-18.md` #1
(*"client side force mount"*): it keeps ACE **vanilla** (§2 `keep-ACE-vanilla`),
keeps the small-byte-patch release model, and works against any server. The
alternative — ACE `GameMessageDDDInterrogation` `1u` → `5u` — remains documented
for server operators but is **not** our ship path.

### Why the patch exists

`client_highres.dat` is the client's 4th dat controller (`m_DatFiles[3]`). Retail
only initialises it when the server's `DDD_InterrogationMessage` advertises
**product bit 4**:

```
acclient.c:293785-293793  (CLCache::OnServerInterrogation)
    this->m_DDDState = 1;
    this->m_EarlySaves.m_num = 0;
    this->m_cbEarlySaves = 0;
    if ( v2->m_dwProductID & 4 )
      CLCache::LoadHighResDat(this);
```

Vanilla ACE sends `1u`, so on an ACE shard the highres dat is never mounted. Once
the HIFI split lands (r8), highres is **load-bearing** — the portal no longer
carries a fallback copy of the superseded textures — so an unmounted highres is
a missing-texture render, not a graceful degrade.

### The patch

One 2-byte NOP that removes the `je` guarding the call:

| key | EOR file offset | VA | before | after | disassembly |
|---|---|---|---|---|---|
| `highres-force-mount` | `0x000FAFA9` | `0x4FAFA9` | `74 05` | `90 90` | `je +5` → 2× `nop` |

```
retail                                    patched
4fafa5: f6 45 10 04  testb $0x4,0x10(%ebp)   4fafa5: f6 45 10 04  testb $0x4,0x10(%ebp)
4fafa9: 74 05        je   0x4fafb0           4fafa9: 90 90        nop; nop
4fafab: e8 40 fe ff ff call 0x4fadf0         4fafab: e8 40 fe ff ff call 0x4fadf0
```

`ecx` still holds `this` at the call (`mov %ecx,%esi` at `0x4FAF8A`, never
clobbered through `0x4FAFAB`) — the `thiscall` is intact. The `testb` is left in
place deliberately: it is harmless (only sets flags, which nothing downstream
reads) and it keeps the site self-documenting.

Signature (invariant prefix + masked needle + invariant suffix), **unique
(count = 1)** in `acclient.eor.orig.exe`:

```
prefix  89 be f4 02 00 00 89 be f8 02 00 00 f6 45 10 04
needle  74 05
suffix  e8 40 fe ff ff 8b 45 08 8b 16
```

**Box-build cross-reference**: this signature **relocates unchanged** to
`acclient.box-4837376.exe` at file `0x000FA409` (count = 1) — the
`LoadHighResDat` `call rel32` happens to be `e8 40 fe ff ff` in both builds. So,
unlike `res-4k-unlock-2` / `dat-version-preserve`, no separate box entry is
needed.

Symbol grounding: `yonneh-acclient.map` (box build, VA = RVA + `0x401000`) —
RVA `0x000F93E0` `CLCache::OnServerInterrogation`, RVA `0x000F9250`
`CLCache::LoadHighResDat`, which are exactly the decomp's `004FA3E0` / `004FA250`.
The EOR build puts the same two functions at `0x4FAF80` / `0x4FADF0`.

### Safety when `client_highres.dat` is ABSENT — proven, not assumed

The concern was that forcing a mount on a missing file could crash a
highres-less install. It cannot, and both guards were read out of the **EOR
binary**, not just the decomp:

1. **The slot always exists.** `CLCache::Init` unconditionally
   `operator new(0x788)`s the 4th `CThreadsafeDiskController` and stores it into
   `m_DatFiles.m_data[3]`, with no product-bit involvement:
   EOR `0x4FABC0 mov 0x1e0(%ecx),%edx / 0x4FABC6 mov %esi,0xc(%edx)`
   (box `0x4FA020` / `0x4FA026`; `0x1E0` = `CLCache::m_DatFiles.m_data`,
   `+0xC` = element 3). So `LoadHighResDat`'s outer guard
   `if (m_DatFiles.m_data[3])` (`acclient.c:293682`; EOR `0x4FADF8`–`0x4FAE03`)
   passes on every client, patched or not.
2. **The body is file-existence-gated.** Everything that touches the disk sits
   inside `if (LookFile::LookForFile(...))`:
   EOR `0x4FAE70 call 0x672900` (= `LookFile::LookForFile(PStringBase<ushort>,
   PStringBase<ushort>, bool)`, map RVA `0x00270960`), then
   `0x4FAE75 test %al,%al`, `0x4FAE7D je 0x4FAF44`. The false arm jumps **past**
   the `DiskConInitInfo` construction, the `DiskController::Init` vcall and the
   `m_DatFileByIDTable::add`, straight into the `LookFile` destructor and the
   return. With no `client_highres.dat` on disk the forced call costs one
   `PStringBase` alloc/free and returns.

**The graceful path is preserved, not bypassed.** A highres-less install boots
and plays exactly as before; the patch is inert there.

### What the file must look like

The mount is not "any file named `client_highres.dat`". `LoadHighResDat` builds
its `DiskConInitInfo` with `PORTAL_DATFILE` and the magic `0x69466948`
(`acclient.c:293710`) — that is ASCII `HiFi`. Read out of the real retail file
(`/mnt/wbterminal2/highres-acquisition/eor2013/client_highres.dat`, read-only,
2026-08-18): header `+0x14C dataSet = 1` (`PORTAL_DATFILE`),
`+0x150 subSet = 0x69466948`, `blockSize = 0x400`, `fileSize = 0x07F00000`.
A custom highres must reproduce both identity fields or `DiskController::Init`
fails and the mount is silently skipped.

**Harder requirement — the iteration record.** Immediately after the (now
unconditional) `LoadHighResDat` call, `OnServerInterrogation` walks **every**
`m_DatFiles` entry and, for each `IsInitialized()` controller, calls
`GetDatFileID()` + `LoadIterationList()`:

```
acclient.c:293815-293823
        if ( ...m_DatFiles.m_data[v4]->vfptr->IsInitialized() )
        {
          v9  = ...m_DatFiles.m_data[v4]->vfptr->GetDatFileID();
          v10 = CAllIterationList::AddIterationList(&response.m_ItersWithKeys, v9);
          if ( !...m_DatFiles.m_data[v4]->vfptr->LoadIterationList(v10) )
            v7 = 0;                       // <- poisons the whole response
        }
...
acclient.c:293829
    if ( v7 )
      CLCache::AdoptAndDeliverMessage(...&response...);   // ONLY sent when v7
```

and `DiskController::LoadIterationList` (`acclient.c:647540-647584`) reads DID
`0xFFFF0001` (`stru_8333B8`, `acclient.c:46578` = `4294901761u`) and requires
`RawData.m_iVersion == 1`, else it returns 0.

⇒ **A force-mounted highres dat that lacks a valid `0xFFFF0001` record makes the
client fail to send its `DDD_InterrogationResponseMessage` at all** — a login
hang, not a texture glitch. The retail file has it (b-tree walked 2026-08-18:
one entry, `id=0xFFFF0001 off=0x07EAC000 size=12 bitflags=0x00010000` — the
version word is the high half of `bitFlags`, `= 1`, exactly what
`LoadIterationList` demands; payload `f1 01 00 00 0f fe ff ff 01 00 00 00`, i.e.
iteration **497**). **`highres_lane.py` must be shown to emit this record before
any custom highres ships.** Add it to the lane's CI fixture check.

### ⚠ READ FIRST — this patch is half of a PAIR

`highres-force-mount` alone is **not** shippable against vanilla ACE: forcing the
mount also makes the client *advertise* the highres dat in its DDD interrogation
response, where it collides with `client_portal.dat`'s id and gets the session
booted at character select (full analysis in § *DDD iteration semantics*). The
owner decided **Option B** on 2026-08-18
(`docs/dat-patch/DECISIONS-2026-08-18.md` item 4): the companion patch
**`highres-advertise-cap`** removes the collision at the source. Ship both or
neither; box gate arm D exercises the pair.

The original blocker write-up follows, because the gate arms still depend on it.

### The blocker `highres-advertise-cap` fixes

Research done the same day (plan item 2.2, full analysis in the
**DDD iteration semantics** section at the end of this file) found a blocker that is **not** in the
client and **not** fixed by this patch:

A mounted highres controller is added to the client's DDD interrogation response
like any other dat (`acclient.c:293815-293823` — the only membership test is
`IsInitialized()`), tagged with `GetDatFileID()`. `client_highres.dat` carries
**`dataSet = 1` = `PORTAL_DATFILE`** in its header (verified at file offset
`0x14C`), so on the wire its `DatFileId` is `1` — the **same tag as
`client_portal.dat`**. Vanilla ACE's `DDDHandler.DDD_InterrogationResponse`
switches on exactly that field (`ACE.Server/Network/Handlers/DDDHandler.cs:45`,
`case 1: // PORTAL`), so the highres entry lands in the portal case, overwrites
`clientPortalDatIntSet`, and its iteration **count** (retail highres = 497) is
compared against the server's portal iteration (live server: 2073). `497 < 2073`
⇒ `clientIsMissingIterations = true` ⇒ with `EnableDATPatching = false`
(the default and the live setting) ⇒
`session.Terminate(SessionTerminationReason.DATsPatchingDisabled)` at
`DDDHandler.cs:165-168`, **ungated by `show_dat_warning`**.

⇒ **Expected outcome of arm B below is a boot at character select.** That is not
a bug in the patch — it is the correct, predicted behaviour, and it *proves* the
mount happened. Arm B is kept in the gate precisely *because* it is the
unambiguous mount proof; **arm D** (force-mount **+** `highres-advertise-cap`) is
the arm that has to reach the world.

Do **not** "work around" it by setting `EnableDATPatching = true` on the box:
with `clientPortalDatIntSet` corrupted to the highres set, ACE would compute
iterations 498…2073 as missing and stream a multi-hundred-MB DDD download **into
`client_portal.dat`** (`DDDHandler.cs:123-146`).

## `highres-advertise-cap` — don't report the highres dat to a server that never asked (SHIPPED 2026-08-19; built 2026-08-18)

**Status: `enabled=False`.** The required companion to `highres-force-mount` —
**ship both or neither**. Owner decision `docs/dat-patch/DECISIONS-2026-08-18.md`
item 4 (Option B). Graduates with force-mount after box gate arm D.

### What it does

`CLCache::OnServerInterrogation` advertises every initialised dat controller in
the DDD interrogation response, so a forced highres mount adds a 4th entry whose
`DatFileId` is `1` — the same tag as `client_portal.dat` — and vanilla ACE boots
the session over it (§ *DDD iteration semantics* for the full chain). This patch
caps the advertise loop at slots 0–2 (portal, local, cell), so the response is
**byte-identical to an unpatched client's** while the mount, the
`m_DatFileByIDTable` registration and highres read-precedence all stay intact.

That is also the semantically honest behaviour: a server that never set product
bit 4 has no business being told about the highres dat.

### Why ONE site and not two — the `m_num` underflow proof

`OnServerInterrogation` reads `m_DatFiles.m_num` (`CLCache+0x1E8`) **exactly
twice**, and there are no others in the function (its length is `0x310` per the
box map, RVA `0xF93E0`→`0xF96F0`; the next `mov eax,[esi+0x1e8]` anywhere in the
exe is at `0x0FC9F1`, far outside):

| site | EOR offset | role |
|---|---|---|
| entry guard | `0x000FAFDB` | `mov 0x1e8(%esi),%eax` + `test %eax,%eax` (`0x4FAFE1`), consumed by the `jbe 0x4FB05C` at `0x4FB00F` — i.e. `if (m_num == 0) skip the loop` |
| **loop bound** | `0x000FB051` | re-read every iteration; `inc %edi; cmp %eax,%edi; jb` |

**Only the loop bound is patched.** The entry guard is deliberately left reading
the real `m_num`, because that is what makes the cap safe in the degenerate
state:

`m_DatFiles.m_num` is provably **0 or 4, and nothing in between**. In
`CLCache::Init` (EOR):


(Byte-identical structure in the box build at `0x4F9D4D`–`0x4F9D91`.) The store
is on the **success path only**; on `grow` failure `m_num` keeps its
constructed `0` (`acclient.c:296171-296173`). So:

| `m_num` | with cap on loop bound only | with cap on BOTH sites |
|---|---|---|
| `4` (every real boot) | guard passes, loop runs slots 0,1,2 — highres omitted ✓ | identical ✓ |
| `0` (grow failed) | guard `test 0,0` → `jbe` taken → **loop skipped**, retail behaviour preserved ✓ | `test 3,3` → `jbe` NOT taken → do-while runs over a **NULL `m_data`** ✗ |

Patching the entry guard as well would **invent a crash retail does not have**,
for zero functional gain (the two forms are identical whenever `m_num == 4`).
Hence the one-site form. It would only be unsafe for `m_num` of 1 or 2, which the
disassembly above rules out.

### What it actually changes

Both sites are in **`UIElement`**, not in the D3D/display code. The client's UI
layout system stores per-element size limits as attributes read through
`UIElement::GetAttribute_Int(key, &out) -> bool` (EoR VA `0x460B30`), with

| key | attribute |
|---|---|
| `0x3C` | MaxHeight |
| `0x3D` | MaxWidth |
| `0x3E` | MinHeight |
| `0x3F` | MinWidth |

(names proven from `acclient.c` `UIElement::ResizeTo`, decomp line 160202 —
`nMaxHeight/nMinHeight/nMaxWidth/nMinWidth`).

**`res-4k-unlock-2` is the load-bearing half.** `UIElement::ResizeTo(w,h)`
(EoR VA `0x463D60`) is the programmatic resize path every element takes when
the window/screen size changes. Retail runs four identical blocks
`call GetAttribute_Int(key,&out); test al,al; je skip; <clamp>; skip:`. Pea
flips each `je` (`74`) to `jmp` (`EB`), so **all four clamps are skipped
unconditionally** and the requested size passes through verbatim. That is what
"unlocks 4K": above the era's supported resolutions the max clamps pin elements
(notably the 3D-view region) below the backbuffer.

**`res-4k-unlock` is the drag-resize half.** `UIElement::MouseResizeElement`
(EoR VA `0x461210`, called only from `UIElement::MouseMove` @ `0x463414`)
clamps a border-dragged element the same way. Pea replaces the `0x3D` and
`0x3C` queries with a literal store of the value (`3840` = `0x0F00`,
`2160` = `0x0870`) into the locals *and* clears the "attribute present" bools,
so the two max-clamp arms are dead. The `3840`/`2160` literals are then never
read — they are self-documenting only.

| key | EOR file offset | VA | function | change |
|---|---|---|---|---|
| `res-4k-unlock`   | `0x0006128D` | `0x46128D` | `UIElement::MouseResizeElement` +0x7D | 70 bytes (see registry) |
| `res-4k-unlock-2` | `0x00063D94` | `0x463D94` | `UIElement::ResizeTo` +0x34 | 4× `74` → `EB` inside an 87-byte needle |

Site 2's four flipped bytes are at file `0x63D94`, `0x63DB0`, `0x63DCC`,

#### Historical note (superseded by the above)

`MouseResizeElement` is `sub esp,0x20` + `push ebx/ebp/esi/edi` → body
`esp = entry_esp − 0x30`, and it returns `ret 8` (epilogue at `0x461659`).
`GetAttribute_Int` is `ret 8` (callee-cleans), so the two `push`es before each
call are the only transient stack delta. Pea's replacement **deletes both push
pairs**, which shifts `esp` by 8 at the two `al` spills that follow them. He
re-based the first (`mov [esp+0x40],al` → `mov [esp+0x38],al` — correct, both
resolve to `entry_esp+0x08`) but **left the second unchanged**:

| spill | original | resolves to | patched | resolves to |
|---|---|---|---|---|
| bool(0x3F) @ `0x461296` | `mov [esp+0x40],al`, esp=E−8 | `entry+0x08` | `mov [esp+0x38],al`, esp=E | `entry+0x08` ✓ |
| bool(0x3E) @ `0x4612BA` | `mov [esp+0x3c],al`, esp=E−8 | `entry+0x04` | `mov [esp+0x3c],al`, esp=E | **`entry+0x0C`** ✗ |

Consequences of the second row:

1. **One-byte stack corruption in the caller.** `entry_esp+0x0C` is the slot
   holding `UIElement::MouseMove`'s **saved ESI** (`push esi` at `0x4633FD`;
   `push ebp; push ebx; call` at `0x463410`–`0x463414`; callee `ret 8` lands
   esp back on it). MouseMove pops it at `0x4634AC`, so a `0`/`1` byte is
   handed back to *MouseMove's* caller as the low byte of its `esi`.
2. **Uninitialised `has_min_height`.** The real bool slot `entry_esp+0x04` is
   never written, and it is the reused `_xWindow` argument slot — so the
   min-height clamp at `0x461320` fires on the low byte of the current mouse X.
   Non-deterministic, though the `min_height` value itself is still correctly
   loaded (the `0x3E` query is untouched).

Both are reached only while actively drag-resizing a UI element by its border,
which is presumably why this has gone unnoticed in years of community use.
**Corrective byte**: `replace[48]` `0x3c` → `0x34` (`mov [esp+0x34],al`) fixes
both at once. ~~It is deliberately not applied.~~ **APPLIED as of 2026-08-18**
(owner decision #2) — see the re-verification block above.

## DDD iteration semantics for a force-mounted highres on vanilla ACE (2026-08-18)

Plan item 2.2 / handoff open item #4, verified rather than assumed. Sources:
`/home/wbterminal/ac-headers/acclient.c` (+ the EOR exe for the machine code),
and the **running** vanilla ACE tree `/home/wbterminal/ace-server/Source/`
(`external/ACE/Source/` is a partial checkout — it has no
`ACE.Server/Network/Handlers/`, so the DDD code is not in it; same commit per the
lane's standing note, and its one local mod, `WorldDatabaseWithEntityCache`, is
unrelated to DDD). **Nothing in either tree was modified.**

### VERDICT: **UNSAFE as-is — CONDITIONAL on a mitigation.**

The client side is clean. The **client + vanilla ACE combination** is not, and it
is broken for the **retail** highres too, not just a custom one. The blocker is a
dat-id collision, not an iteration policy.

### (a) Is the highres dat exempt from DDD iteration enforcement? **NO.**

It is not exempt, and the product bit does not exempt it. Once the controller is
initialised, it is reported like any other dat:

```
acclient.c:293812-293824  (CLCache::OnServerInterrogation, right after the mount)
      do {
        if ( ...m_DatFiles.m_data[v4]->vfptr->IsInitialized() ) {
          v9  = ...->GetDatFileID();
          v10 = CAllIterationList::AddIterationList(&response.m_ItersWithKeys, v9);
          if ( !...->LoadIterationList(v10) )  v7 = 0;
        }
        ++v4;
      } while ( v4 < v3->m_DatFiles.m_num );
```

The **only** membership test is `IsInitialized()`. There is no highres
special-case and no product-bit re-check. Because `CLCache::Init` sizes
`m_DatFiles` to 4 and highres is slot 3, a forced mount makes the response carry
**four** entries instead of three, with highres last. ACE reads all of them
(`ACE.Server/Network/Structure/CAllIterationList.cs:18-21` — `numElements`, then
that many `PTaggedIterationList`).

### (b) Does anything compare the highres iteration when bit 4 is unset? **YES — as if it were the portal dat.**

The wire tag is `DiskConBase::GetDatFileID` = `(data_set_lm << 32) |
data_subset_lm` (`acclient.c:291609-291614`; the 64-bit return puts `data_set` in
EDX and `data_subset` in EAX), serialized **low dword first**
(`acclient.c:654463-654464`). ACE reads that pair as
`DatFileType` then `DatFileId` (`PTaggedIterationList.cs:29-31`) — so
`DatFileId == data_set_lm`. Confirmed by ACE's own writer
(`GameMessageDDDBeginDDD.cs:31-45`: Portal → `Write(0); Write(1)`, Cell →
`Write(1); Write(2)`, Language → `Write(1); Write(3)`).

`client_highres.dat` carries **`dataSet = 1` = `PORTAL_DATFILE`**:

- the client passes `PORTAL_DATFILE, 0x69466948u` when building the init-info
  (`acclient.c:293705-293716`), and
- `DiskController::InitFile` then **overwrites the init-info from the file header
  and never compares it** (`acclient.c:647924-647925`, and again at
  `:647953-647956`) — `PORTAL_DATFILE` occurs exactly once in the whole decomp,
  so nothing validates it; and
- the real retail file's header says so: `+0x14C dataSet = 1`,
  `+0x150 subSet = 0x69466948` (read directly, 2026-08-18).
- ACE knows this too: `ACE.DatLoader/DatDatabaseType.cs:5` —
  `Portal = 1, // client_portal.dat and client_highres.dat both have this value`.

So the highres entry hits `case 1: // PORTAL` in
`ACE.Server/Network/Handlers/DDDHandler.cs:45-47`, **overwrites**
`clientPortalDatIntSet` (`:48`) and is compared against the *portal* iteration:

```csharp
DDDHandler.cs:48-61
    case 1: // PORTAL
        clientPortalDatIntSet = entry.List;
        if (entry.List.Iterations < DatManager.PortalDat.Iteration)   { …; clientIsMissingIterations = true; }
        else if (entry.List.Iterations > DatManager.PortalDat.Iteration) { …; clientHasExtraIterations = true; }
```

`Iterations` is the **count** field of `CMostlyConsecutiveIntSet`
(`CMostlyConsecutiveIntSet.cs:31`). Retail highres = **497** (record `0xFFFF0001`
at file offset `0x07EAC000`, 12 bytes `f1 01 00 00 0f fe ff ff 01 00 00 00`,
b-tree-walked 2026-08-18). The live server's portal iteration is **2073**
(`ACE_Log.txt`: `client_portal.dat: 2073 | client_cell_1.dat: 982 |
client_Local_English.dat: 994 | no update required`).

`497 < 2073` ⇒ `clientIsMissingIterations = true`. `EnableDATPatching` defaults
false (`ACE.Common/DDDConfiguration.cs:11`) and is false on the live server
(`bin/Release/net10.0/Config.js:42`), so:

```csharp
DDDHandler.cs:165-168
    else if (clientIsMissingIterations && !enableDATpatching)
    {
        var msg = PropertyManager.GetString("dat_older_warning_msg").Item;
        session.Terminate(SessionTerminationReason.DATsPatchingDisabled, new GameMessageBootAccount(...));
    }
```

That `Terminate` is **not** gated on `show_dat_warning` (unlike the warning paths
at `:52`, `:118`, `:207`). The interrogation is sent with the character list
(`AuthenticationHandler.cs:259-263`), so **the client is booted at character
select, before enter-world**. A *higher* custom iteration count is equally fatal
via `clientHasExtraIterations` → `DDDHandler.cs:117-120`
`Terminate(DATsNewerThanServer)`. The only surviving value is exactly
`== DatManager.PortalDat.Iteration`, which is coupled to whatever portal dat the
server happens to load — not a design we can ship.

For completeness: ACE **does** open `client_highres.dat` if present
(`ACE.DatLoader/DatManager.cs:64-72`), but `DatManager.HighResDat` is referenced
only by admin/console export commands (`DeveloperCommands.cs:1218`,
`ConsoleCommands.cs:55/66/175-181`) — **zero** references from `DDDHandler` or
`DDDManager`. So nothing ever compares against a highres iteration; the damage is
entirely the `DatFileId == 1` collision.

### (c) Dat-repair / purge / re-download risk

- **No client-side integrity scanner exists.** The only repair-shaped code is
  `BTree::RecoverTransaction` (`acclient.c:647934`), reached only when
  `CLBlockAllocator::OpenDataFile` reports an interrupted write transaction.
- **Purges are entirely server-driven and cannot target highres from vanilla
  ACE.** `CLCache::WorkerExecuteBeginDDDRequest` (`acclient.c:290945-290958`)
  matches the server's `idDatFile` against `GetDatFileID()` on the **full 64
  bits**, `break`s at the first match, and skips unknown ids
  (`if (v7 >= 4) goto LABEL_17`). ACE only ever emits `(0,1)/(1,2)/(1,3)` and
  only purges Cell (`GameMessageDDDBeginDDD.cs:47-56`), so the highres controller
  is never a purge or download target.
- **The real re-download risk is the reverse**: if anyone sets
  `EnableDATPatching = true`, `clientPortalDatIntSet` (now the *highres* set)
  drives `DDDManager.GetMissingIterations` (`DDDHandler.cs:123`), and iterations
  498…2073 are streamed **into `client_portal.dat`** (`:135-146`). Do not enable
  it while testing this patch.
- **Mount failure is benign.** `CThreadsafeDiskController::InitFile`
  (`acclient.c:291982-291997`) shows an `"ERROR"` modal
  (`PlatformString::DisplayString(0xCE)`) and calls `DiskController::Close`,
  which clears `initialized_fm` — so a failed highres controller drops out of the
  interrogation list and the client proceeds normally. Pack-version mismatch is
  the same story: `InitFile` returns `-6` (`acclient.c:647926-647930`) unless the
  file's `eng_pack_vnum`/`game_pack_vnum` match `DBCache::s_EngDataPackVer` /
  `s_GameDataPackVer` (retail highres and portal both carry EngPack 110,
  GamePack 0).
- **One genuine login-hang path**: `acclient.c:293819-293820` — if any
  controller's `LoadIterationList` fails, `v7 = 0` and `:293828-293829` then
  **skips sending the response entirely**. In practice `InitFile` already aborts
  on that failure, but a custom highres that mounts yet lacks a valid
  `0xFFFF0001` record is the shape to watch. **Not runtime-verified.**
- **Hash-key collision**: `LoadHighResDat` registers the controller in
  `m_DatFileByIDTable` keyed by `GetDatFileID()` (`acclient.c:293728-293733`).
  Retail keys differ only via the subset (`0x00000001_69466948` vs
  `0x00000001_00000000`), so a custom highres with `subSet = 0` would collide
  with the portal controller.

### Options — **OPTION B DECIDED AND BUILT 2026-08-18** (owner, DECISIONS-2026-08-18 item 4)

**Option A — data-side: give our custom highres a `dataSet` outside `{1,2,3}`**
(header offset `0x14C`, e.g. `4`), keeping `subSet = 0x69466948`. ACE's
`switch (entry.DatFileId)` then matches no case and ignores the entry entirely;
no comparison, no boot. Client-side this looks inert — `data_set_lm` is only
stored and folded into `GetDatFileID` (`acclient.c:291613`), `InitFile` takes it
from the header without comparing (`:647924`), and highres precedence in
`GetDiskController` (`:292513-292518`) uses slot 3 + `IsMember`, never the
dataset. Costs nothing at ship time. **Does not help with the *retail* highres**,
and makes our file non-standard for third-party tooling.

**Option B — a second byte patch: don't advertise slot 3. ← CHOSEN, now shipped
as the `highres-advertise-cap` registry entry** (full write-up in its own section
above). Caps the advertise loop bound at 3 so slots 0–2 are reported exactly as
retail and slot 3 is silently omitted, leaving the mount, the
`m_DatFileByIDTable` registration and highres read precedence fully intact. Works
for the retail highres **and** any custom-iteration highres, and keeps our dat
byte-shaped like retail's. Implemented as **one** site — the loop bound at EOR
`0x000FB051` — deliberately **not** the entry guard at `0x000FAFDB`; see the
`m_num` underflow proof in that section. **Built and byte-verified; still
untested at runtime — box gate arm D.**

**Option C — match the server's portal iteration count.** Rejected: it couples
our highres to whatever `client_portal.dat` the server loads and breaks on any
server-side dat change.

## `dat-align-lfa` — DAT-parser pointer alignment for >2GB (LAA) buffers (SHIPPED 2026-08-23; owner-verified same day)

189 sites: `and r32, 0x80000003` → `and r32, 0x00000003` (one byte per site —
the imm sign byte). Registered as an `AlignIdiomPatch` (idiom-scan, not a
single unique signature): each site is located by the imm32 dword plus an AND
opcode immediately before it (`25` = and eax,imm32 or `81 /4`) plus BOTH fixup
markers in the following 28-byte window (`04 00 00 00` from `mov r32,4` and
`83 c8..cf fc` = `or r32,-4`). The window filter is what skips the exe's 2
non-idiom uses of the constant. The scan must census EXACTLY 189 sites of one
form or it refuses.

### Root cause (minidump-proven 2026-08-23)

acclient is large-address-aware (PE characteristics 0x012E). Under dense-dat
residency (r9) the process exceeds 2 GB, so cache/archive buffers land at
addresses ≥ 0x80000000. Retail's archive 4-byte alignment idiom computes
`(signed int)cursor % 4`; a pointer ≥ 0x80000000 is negative as a signed int,
the modulo returns the wrong pad count, the read cursor desyncs from the real
record layout, and a later read walks off the buffer → AV. Proof: dump
`acclient.exe.18236.dmp` faulted reading `0x9A049000` in `AnimData::UnPack+0x16`
from `MotionData::UnPack`, whose align idiom at VA 0x5271A6 is exactly this
pattern; the record being parsed (MotionTable 0x09000068) is byte-identical to
retail base — parser math, not data. Full narrative:
`WorldBuilder-ACME-Edition/docs/lights-port/HANDOFF-2026-08-23-crash-investigation.md`.

### Correctness

For any pointer < 2 GB, `(signed)p % 4` and `p & 3` produce identical results
(the value is non-negative, so the `jns` skips the fixup either way and the
AND result is unchanged by clearing the imm sign bit — that bit only reports
sign for negative inputs). The patched `and r32,3` always yields 0..3, so the
`jns` fixup branch (`dec; or r,-4; inc`) is never taken: the sub-2GB path is
byte-behavior-identical, and the ≥2GB path becomes correct instead of wrong.

### Wine / linux (T4 buildbox) validity — static analysis 2026-08-23

The patch is pure x86 integer ALU with no OS interaction, so it behaves
identically under wine. Wine honors the LAA PE flag, and a 32-bit process on a
64-bit linux kernel has no 2 GB kernel split — an LAA process there gets ~4 GB
of address space, and wine/DXVK's own in-process allocations (shader caches,
staging buffers) push the heap high sooner. High pointers are therefore MORE
likely under the wine/T4 stack than on Windows, i.e. this fix is REQUIRED
there, not merely compatible. Wine does not validate PE checksums for
executables (only drivers), and the checksum is recomputed anyway.
⚠ The buildbox `~/ac_client` kit was staged before this patch existed — redeploy
`acclient.eor.patched.exe` from this directory on next boot before any wine gate.
