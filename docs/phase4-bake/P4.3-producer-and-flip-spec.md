## 0. GROUND-TRUTH RECONCILIATION (read first — the codec is already built)

Several pieces the older A01/A12 drafts called "remaining" are **already
implemented in the working tree** (uncommitted, `git status` shows
`M animated_scenery.js / statics.js / suite_assets.js / suite-bake/src/lib.rs`,
`?? suite-bake/src/windclip.rs`). This spec MUST match what is built, not the
older draft. The deltas from the prompt's draft text:

1. **The on-disk artifact is the RAW CODEC PAYLOAD, not a `SuiteBlob` container,
   and not the "WCLP 64-byte header" format.** Decisive evidence:
   - `fetch_suite_artifact` (`apps/holtburger-web/src/lib.rs:2514`) returns the
     fetched bytes **verbatim** — it does **not** strip any `HSB1` container.
   - The JS decoder (`scene3d/suite_assets.js:113-159`) reads `num_parts` at
     **byte offset 0** (`dv.getUint32(0,true)`). If the file began with the
     `SuiteBlob` magic `b"HSB1"`, offset-0 would parse as `num_parts =
     0x31425348` → `ff` overflow → `return null` → **wind silently never uses
     the bake**.
   - ⇒ The file the producer writes = **`WindClip::encode_payload()`** bytes
     (the 16-byte header + buckets + rig), **NOT** `WindClip::encode()` (the
     container-wrapped form). `crates/holtburger-suite-bake/src/windclip.rs`
     deliberately separates `encode_payload()` (raw, line 159) from `encode()`
     (container, line 189). **Use `encode_payload()` semantics.**
   - The `SuiteBlob` container + advisory `content_hash` remain available for a
     **future** transport that strips on the wasm side; they are **inert** in
     the P4.3 wire path. (Open question OQ-1 below tracks the comment drift in
     `suite_assets.js:92` which says "container … already stripped by the wasm
     fetch side" — today nothing strips; the file is raw payload.)

2. **The implemented payload header carries NO per-param echo** beyond `fps`.
   The 64-byte `WCLP` header with 8 baked-param floats (loop/amp/dir/strength/…)
   from the A01 §3 draft was **not** implemented. The real header is 16 bytes:
   `num_parts u32 | num_frames u32 | k u32 | fps f32`
   (`windclip.rs:14-18`, `suite_assets.js:97-100`). Consequence: **`dirDeg` and
   `strength` are frozen into the baked frames** (Option A — baked-authoritative;
   the `?treeWindDir` / `?treeWindStrength` URL overrides are ignored when a baked
   clip is consumed). This is intentional and is exactly why the flip is `[C]`
   and stays default-off. See §B firewall note.

3. **Already done (do NOT re-spec):**
   - Rust codec `windclip.rs` — `WindClip{num_parts,num_frames,fps,buckets,rig}`,
     `encode_payload`/`decode_payload`/`from_blob`/`decode`/`fingerprint`,
     8 unit tests (`cargo test -p holtburger-suite-bake` green).
   - JS decoder `registerSuiteDecoder("windclip", …)` (`suite_assets.js:113`).
   - `attachWindTrees` returns `{built, failed}` (`animated_scenery.js:495-558`).
   - statics.js coverage-gated re-freeze `statics = statics.concat(failed)` at
     **both** call-sites (`statics.js:1741-1742` per-LB, `2304-2305` ring).
   - `fetch_suite_artifact` transport + cache (`lib.rs:2425-2545`, committed).

   What is **left** = exactly the two deliverables A and B in this doc.

4. **Codec payload layout (authoritative — `windclip.rs:14-27`,
   `suite_assets.js:97-104`), all little-endian:**

   ```text
   off  size  field
   0    4     num_parts  : u32
   4    4     num_frames : u32        (= max(2, round(fps*loopSeconds)+1); 121 @ defaults)
   8    4     k          : u32        (phase-bucket count; MUST == live K = 4)
   12   4     fps        : f32        (30 @ defaults)
   --- k bucket blocks, BUCKET-MAJOR, b = 0..k ---
   16 + b*BS   bucket[b] : (num_frames*num_parts*7) × f32, FRAME-MAJOR then part-major
                           value(f,p,c) = data[(f*num_parts + p)*7 + c]
                           c: 0=ox 1=oy 2=oz 3=qw 4=qx 5=qy 6=qz   (AC quaternion wxyz)
               BS = num_frames*num_parts*7*4 bytes
   --- rig, p = 0..num_parts, 44 bytes each ---
   16 + k*BS + p*44 : pivot.x,y,z, weight, rest_o.x,y,z, rest_q.w,x,y,z   (11 × f32)
   total = 16 + k*num_frames*num_parts*7*4 + num_parts*44   (always %4 == 0)
   ```

   **Bucket-order contract (load-bearing):** bucket `b` MUST be produced at
   `windParams.phaseOffset = (b/k)*2π`, emitted ascending `b`. Runtime selects
   block `b = floor(hash01(key)*K) % K` (`animated_scenery.js:550`) and expects
   exactly that phase baked in.

5. **Dist serving-root (A12 R10 — RESOLVED):** `scripts/serve.py` web root is
   `external/holtburger/`; `external/holtburger/dist` is a **symlink** →
   `/mnt/wbterminal2/holtburger-dist` (default `HOLTBURGER_DIST`; **no `-v2`**,
   no `holtburger-dist-v2` on disk). `SUITE_BASE_URL = "../../dist/suite/"`
   (`suite_assets.js:15`) resolves from the page at
   `/apps/holtburger-web/index.html` to server-root `/dist/suite/` =
   `/mnt/wbterminal2/holtburger-dist/suite/`. **The producer writes to

### A.3 Per-DID pipeline (in `page.evaluate`, byte-faithful to `buildOneWind`)

For each DID, run inside the page (so wasm + materialCache + V8 Math are the
runtime's own):

1. `const bundle = await wasm.fetchBuildingPlacement(did)`; `partCount =
   bundle.partCount|0`; if `0` → skip DID (matches `buildOneWind:433`).
2. `const partMeshes = bundle.takePartMeshes()` (ONE-SHOT, `lib.rs:9895` — read
   exactly once, mirror `buildOneWind:434`); `const hinge =
   bundle.takePartHingeFrames?.() ?? []`; `bundle.free?.()`.
3. **R4 material gate (BLOCKING for byte-identity):** for each part, walk
   `meshToGeometryGroups(wasmMesh)`, and for each group resolve
   `await materialCache.get(sid, spFetch)` and **only include the group's
   vertices in `partBBox` when BOTH `grp.geometry` AND `mat` are truthy** — i.e.
   exclude verts whose surface material fails to load. This is the exact gate at
   `animated_scenery.js:455-468`. A walk that ignores the gate (e.g. a C#
   `rig-inputs.json` route, or `walk_setup_parts_with_geom` over ALL verts) bakes
   a **different** bounding box → **different rig → non-byte-identical sway**.
   The producer reuses `getOrCreateMaterialCache(scene3d)` +
   `surfacePixelsFetcher(wasm)` so the gate is the runtime's, not a re-port.
   - Use the same `_unionBox` merge + cx/cy/cz re-center (`buildOneWind:470-474`)
     and the `partBBox(null)` empty-box fallback for a part with no surviving
     group (`:476`).
   - **Per-DID assert:** every part resolves at least the same surfaces the
     runtime would; if any surface fails to load, **DO NOT ship that DID's clip**
     (skip + loud warn) — a partially-gated box is worse than no bake (the peel
     fallback then keeps the DID frozen, byte-identical).
4. `const rig = buildBboxRig(partBoxes, hinge).rigs;` (`wind_rig.js:113`, the
   `.rigs` unwrap exactly as `buildOneWind:486`).
5. For `b in 0..K`: `buildTreeWindClip(partCount, rig, {dirDeg:135, strength:1,
   phaseOffset:(b/K)*2π})` → collect `frames` (Float32Array, frame-major).
6. Marshal back to Node: return `{ did, numParts:partCount, numFrames, fps,
   buckets:[Array.from(framesB)…], rig:[{pivot,weight,rest}…] }`. (Float arrays
   cross the CDP bridge as JSON numbers — see A.4 for the bit-exactness method;
   to avoid float-string round-trip risk, prefer transferring the **raw bytes**:
   in-page pack each bucket's `frames` into a `Uint8Array` via
   `DataView.setFloat32(LE)` and return base64, so Node re-emits the **exact
   bytes** with zero re-encode. See A.5.)

### A.4 Encoding the payload (Node side)

Pack `WindClip::encode_payload()` semantics **in JS** (the producer is Node-only;
re-porting the 16-byte framing is trivial and deterministic — no math, pure
layout). For DID with `numParts, numFrames, k=4, fps`:

```text
buf = new Uint8Array(16 + k*numFrames*numParts*7*4 + numParts*44)
dv  = new DataView(buf.buffer)
dv.setUint32(0,  numParts, true)
dv.setUint32(4,  numFrames, true)
dv.setUint32(8,  k,         true)
dv.setFloat32(12, fps,      true)
o = 16
for b in 0..k:        for i in 0..(numFrames*numParts*7): dv.setFloat32(o, bucket[b][i], true); o+=4
for p in 0..numParts: write pivot.x,y,z, weight, rest.o.x,y,z, rest.q[0..3]  (11 f32 LE); o+=44
```

`rest.q` is AC **wxyz** order — write `[q[0],q[1],q[2],q[3]]` **unchanged**
(`buildBboxRig` already stores `[w,x,y,z]`; the JS decoder hands it straight to
`buildSceneryAnimationClip` which does the wxyz→xyzw THREE conversion — the
producer must NOT reorder).

### A.5 Byte-identity-BY-CONSTRUCTION (the proof method)

The producer does **NOT** re-derive `sin/cos` in Node (that is the ULP-divergence
trap A01 §5.2). The `frames` are produced by the **unchanged in-page
`buildTreeWindClip`** (V8 math, the runtime's own), then **byte-copied** into the
payload via `DataView.setFloat32(LE)`. The JS decoder reads them back via
`getFloat32(LE)` → **identical bits** (pure memcpy round-trip, zero
recomputation). Therefore:

> **Claim:** for every DID and bucket `b`,
> `decode(baked).bucketFrames(b)` equals
> `buildTreeWindClip(numParts, rig, {…,phaseOffset:(b/K)*2π}).frames`
> **bit-for-bit**, by construction (no float recompute between produce and
> store).

**Gates the producer MUST run (`--verify`, fail-loud, only passing DIDs ship):**

1. **In-page round-trip (primary):** in the SAME page context, after packing
   `buf`, decode it through the registered JS decoder
   (`import('./suite_assets.js')` → the `windclip` decoder, or inline the same
   reads) and assert, via a `Uint32Array` view (compare **bits**, not float
   `===`, so `NaN`/`-0` are exact): `new Uint32Array(decoded.bucketFrames(b).buffer)`
   equals `new Uint32Array(goldenFramesB.buffer)` for all `b`, and `rig` floats
   match. This catches any pack-order bug.
2. **Rust cross-check (framing parity):** feed the produced payload bytes to
   `WindClip::decode_payload` (a tiny `cargo run -p holtburger-suite-bake
   --example verify_windclip <file>` the implementer adds, OR a `#[test]` that
   loads a fixture) and assert `decode_payload(bytes).encode_payload() == bytes`
   (round-trips) — confirms the JS framing == the Rust codec framing exactly. (If
   added as an example, build via `PATH="$HOME/.cargo/bin:$PATH" capped-build
   cargo build -p holtburger-suite-bake --example verify_windclip`; never
   `--workspace`.)
3. **Determinism:** re-run the whole bake; assert identical `sha256` per file
   (frames are deterministic; pack is deterministic). Any drift = a
   nondeterminism bug — block the bake.

```js
// in attachWindTrees ON branch:

                               { frames: clip.bucketFrames(bucket),
                                 numFrames: clip.numFrames, fps: clip.fps });
// in getOrCreateWindGroup:
if (bakedClip) { ({ frames, numFrames, fps } = bakedClip); }
else           { ({ frames, numFrames, fps } = windBend.buildClip({ numParts, rig }, windParams)); }
```

`bucketFrames(bucket)` is **byte-identical** to what
`windBend.buildClip(...,{...,phaseOffset:(bucket/K)*2π})` would synthesize
(proven §A.5), and is the exact frame-major layout `buildSceneryAnimationClip`
expects (`:398`) — so the downstream (template/mixer/action) is **unchanged**.
`numParts` from the clip MUST equal `r.partCount` (the producer baked the same
material-gated part walk); assert and, on mismatch, treat as a miss →
`failed.push(p)` (a stale bake at a different part count must not animate
wrong).

## OPEN QUESTIONS

- **OQ-1 (comment drift, non-blocking):** `suite_assets.js:92` says the windclip
  bytes are "the SuiteBlob PAYLOAD (the container … was already stripped by the
  wasm fetch side)" — but `fetch_suite_artifact` (`lib.rs:2514`) strips nothing;
  the on-disk file IS the raw payload. The producer therefore writes
  `encode_payload()` bytes (NOT the `HSB1` container). Confirm this is the
  intended contract (it is the only one the current decoder accepts) and fix the
  comment in a later janitorial pass.
- **OQ-2 (R4 fidelity verification):** the producer re-composes `buildOneWind`'s
  material-gated part-box walk from exported helpers; `buildOneWind` itself is
  module-internal (`animated_scenery.js:421`, not exported). The byte-identity of
  the rig rests on that re-composition matching `buildOneWind` line-for-line. A
  stronger gate would be a tiny diag export (e.g. `window.__dumpWindRig(did)`
  returning `_windRigCache.get(did)` after one real `attachWindTrees` pass) so
  the producer can diff its rig against the runtime's. That is a 1-line app-code
  add (out of scope here — flagged for the producer-implementer to consider).
- **OQ-3 (pre-warm vs one-load-frozen):** under `?windBake=on` the first load of
  an LB with a cold suite cache renders frozen for one frame-budget then animates
  after the async fetch resolves. The recommended pre-warm loop (B.2) shrinks but
  does not eliminate this. Confirm on the 1070 eye-test that the transition is
  not visually jarring; if it is, gate the wind-tree build on suite readiness
  (await the 6 small fetches at scene init) rather than lazy per-LB.
- **OQ-4 (dist root for the bake write):** confirmed serving root is
  `${HOLTBURGER_DIST:-/mnt/wbterminal2/holtburger-dist}/suite/` via the
  `external/holtburger/dist` symlink (§0.5). If the bake box uses a different
  `HOLTBURGER_DIST`, the producer must write to *that* root's `suite/`, not a
  hardcoded path — read the env, fall back to the default, and assert the
  resolved dir is the symlink target serve.py is using.
