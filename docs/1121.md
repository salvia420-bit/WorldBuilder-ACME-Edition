## 2. NEW verified fact — the boot-stall grace is ACE's 60 s network-timeout reap, not a "~25 s session grace"

The appendix (T04) prescribed a 25 s quiet-gap. Live 10-boot gate at
gap=25 s: **alternating PASS/FAIL** — every boot after an *in-world*
session stalled; every boot after a *stalled* one passed. Mechanism: this
harness's `close()` kills the browser without any goodbye ACE can see
(wsbridge is WS↔UDP; UDP has no close), so ACE holds the session until
its **60 s network timeout** — the same constant the keepaliveWorker work
documented. 25 s only covers gracefully-ended sessions. At gap=65 s
(60 s reap + margin): **10/10 green, 0 console errors, inWorldMs
5,265–6,894**. Defaults set to 65 s in boot.mjs, battery `--quietGapMs`,
networker-ab.sh; comments + url-flags prose corrected. (s12's "130 s
retry cleared every stall" is consistent: 130 > 60.)

## 5b. Renderer-death diagnosis (user-directed mid-session: "consider if the crashes are fixable")

The battery session fragmentation is "eval-timeout (renderer dead?)"
aborts at heavy POIs. Evidence assembled this session:
- Batteries run `nullRender=1` — SwiftShader does NO per-frame raster
  work, so "SwiftShader crash" is a misnomer; the failing unit is the
  Chromium RENDERER PROCESS (or a wedged main thread).
- No kernel OOM-kill records for the window.
- Arm A final row: `parked=462, evicted=0` across 62 stops — warm-park
  retained EVERY landblock; the pool's 256 MB self-accounting
  (`?warmParkBudgetMb`, landblock_lru.js) never triggered true-dispose,
  but that accounting counts only geometry arrays + texture bytes — NOT
  three.js object overhead, JS objects, or the wasm linear memory — so
  real renderer RSS runs far past it. Accumulation ⇒ late-session
  deaths fits the observed per-session n=4..19 fragmentation.
- SwiftShader itself has a runtime knob file if ever needed
  (`SwiftShader.ini`, `[Processor] ThreadCount/AffinityMask` — context7
  /google/swiftshader RuntimeConfiguration.md); tangential under
  nullRender.
- LANDED: battery driver now ARMS `page.on('crash')` and labels aborts
  `renderer-crash (page crash event fired)` vs `eval-timeout
  (main-thread hang; no crash event)` — crash vs hang is a different
  bug class and the old label guessed.
- **Probe verdict (scripts/net-review/renderer-crash-probe.mjs,
  committed; reproduced in 8 heavy-town hops):
  it is a RENDERER-PROCESS CRASH, not a hang** — `page.on('crash')`
  fired, evaluate threw "Target crashed". Trajectory: **JS heap FLAT at
  93 MB the entire run while renderer RSS climbed 532 → 1,629 → 2,096 →
  2,714 → ~2,790 MB and the process died at ~2.8 GB** (boot →
  Arwic → Tou-Tou → Lytelthorpe → TownNetwork/TN/Ayan/Cragstone plateau
  → dead at Zaikhal). ~250–600 MB of RSS per cold heavy town, none of
  it JS-heap.
- Diagnosis: the growth lives OUTSIDE the JS heap — wasm linear memory
  (shard/decode caches, negative caches, walk-dedup state) + geometry
  ArrayBuffers — exactly the surface the park pool's 256 MB
  self-accounting (`?warmParkBudgetMb`) cannot see (arm A: parked=462,
  evicted=0). SwiftShader is NOT implicated (nullRender; no raster
  work; RSS grows with decode/bake, not frames).
- Fixable? YES, and it is the plan we already have: the S14 wasm batch
  (B1 refcounted byte-budget cache + MODEL_TRI_CACHE eviction upgrade)
  attacks the dominant wasm-side growth directly; A15 residency (grid +
  UseTime park retention) bounds the JS/geometry side; a park budget
  that also counts wasm `memory.buffer.byteLength` growth is the cheap
  canary to add in S14 (expose it in `dat_decode_diag()` and fail
  ci-smoke S5 on unbounded growth). Until then: `--maxStops` fixed
  sessions keep batteries age-matched through the deaths (they did,
  twice, tonight), and the driver now labels crash vs hang precisely.
