## 2. Bug A — Roads painted too wide

### 2.1 What the code does today

Roads in `emit-dynamic-site` are painted **inside the terrain shader** by bilinear-blending the per-vertex road flag across the 4 cell corners and mixing a road texture in by the resulting fractional mask.

- Per-vertex road bit extracted from the 9×9 grid:
  `external/holtburger/crates/holtburger-dat/src/landblock.rs:114-116` — `road_type()` reads terrain bits 0-1.
- Road code propagated through terrain subdivision unchanged:
  `external/holtburger/crates/holtburger-dat/src/terrain_subdiv.rs:475,502,610`.
- Per-vertex road encoded into the G channel of `uVertexTypes` as `roadCode * 64`:
  `external/holtburger/apps/holtburger-web/scene3d/adapter.js:287-302`.
- Per-vertex road sampler in the shader:
  `external/holtburger/apps/holtburger-web/scene3d/terrain.js:443-448` — returns 1.0 if G > 0.125 else 0.0.
- **Bilinear cell-level road mask** (the load-bearing line):
  `external/holtburger/apps/holtburger-web/scene3d/terrain.js:520-530`
  ```glsl
  float roadMask = r00 * w00 + r10 * w10 + r01 * w01 + r11 * w11;
  if (roadMask > 0.001) {
    vec3 roadColor = texture(uRoadTexture, vGridUv * uRoadTileScale).rgb;
    result = mix(result, roadColor, roadMask);
  }
  ```
- Road tile scale: `external/holtburger/apps/holtburger-web/scene3d/terrain.js:1073-1078` — `uRoadTileScale = 4.0` (≈ one tile per 6 m across the 24 m cell). Comment claims this matches retail.

### 2.2 What retail does

- **`_road_width = 5.0` metres** is the retail-side road-width constant, returned from `LandDefs::get_vars`:
  `~/ac-headers/acclient.c:467309-467319`.
- Retail road code extraction uses discrete bit-masking with explicit `switch`/case patterns (`0xF, 0xE, 0xD, 0xB, 0x7, 0x0`) inside `TexMerge::GetRoadCode`:
  `~/ac-headers/acclient.c:304565-304619`.

### 2.3 Hypothesis (CANDIDATE — pending empirical validation)

The bilinear blend of the corner road flags produces a **continuous 0..1 road-presence gradient across non-road cells adjacent to road vertices**. The shader then mixes the road texture in whenever the mask exceeds `0.001`. Any cell with even one road-flagged corner will be partially painted as road, which visually extends the road **a full cell (24 m) past the actual road vertices in each direction** — instead of the ~5 m retail-style width.

Why this is a candidate (not proven):

- The retail-side constant `_road_width = 5.0` argues for a discrete-width model, not a bilinear-blended one — **but we have not yet traced where 5.0 m enters drawn geometry in retail**. The bilinear-vs-discrete framing rests on inference, not on a retail code path.
- The `0.001` threshold at terrain.js:526 is unexplained (why 0.001 and not 0.5?). Empirical validation pending — see GROUND-A.3 and the bilinear-blend offline simulation in §4.
- The shader comment at terrain.js:511-519 acknowledges this is a deliberate departure from the prior overlay-quad approach — i.e. this is a known new code path that has not been visually or numerically compared against retail.

## 3. Bug B — Trees and scenery missing

### 3.1 What we know is NOT the problem

- **Bake is correct.** Per `docs/scenery-bake-b5-collision-parity-report.md`, the Rust scenery bake matches ACE bit-for-bit on **16,700 placements** across the 13×13 Holtburg ring. If trees are missing on screen, **the placements exist in the bake**.
- Ring radius is correct since 2026-05-16: `external/holtburger/apps/holtburger-web/scene3d/index.js:112` sets `STATICS_RING_RADIUS = 6` (full 13×13).

### 3.2 Candidate hypothesis — outdoor visibility gate (pending runtime evidence)

In `external/holtburger/apps/holtburger-web/scene3d/cells.js:583-595`, the whole outdoor render set (terrain + buildings + **statics**) is toggled by a single `wantOutdoor = !isIndoor` flag:

```js
if (scene3d.staticsGroup && scene3d.staticsGroup.visible !== wantOutdoor) {
  scene3d.staticsGroup.visible = wantOutdoor;
}
```

If `isCurrentCellIndoor()` ever returns `true` for the player's current cell at Holtburg — even momentarily during a position-update race — every tree, rock, fence, and scenery prop on the entire ring disappears in one frame. Holtburg has 123 EnvCells inside its buildings, so the indoor flag has many opportunities to flip incorrectly.

**Caveat:** the gate *exists* and *could* flip, but we have no runtime telemetry showing it ever does flip wrong at Holtburg. The "strongest hypothesis" label has been downgraded to "candidate" until gate-flip telemetry lands (see §3.4).

### 3.3 Secondary hypotheses

- **Silent model-fetch skip** at `external/holtburger/apps/holtburger-web/scene3d/statics.js:1206`:
  ```js
  if (!primary.geomByModel.has(placement.modelId)) continue;
  ```
  Any placement whose model failed to fetch is silently dropped from the InstancedMesh. Net effect: fewer trees, no error. **`skippedNoMesh` already accumulates in the `[phase7.2] statics` log** at `statics.js:978, 1168` — but as a ring-wide aggregate. GROUND-B.4 (per-LB break-out) is required to be diagnostic at Holtburg specifically.
- **LOD cap** at `statics.js:130`: `LOD_DISTANCE_M = 100.0`. At a 192 m landblock, anything past one cell vanishes. Holtburg has dense scenery — most of it is within 100 m of the player, so this is unlikely to fully explain the drop, but it can compound with the gate.
- **Draw-call reduction follow-on (FU2)** from `external/holtburger/docs/fps-perf-followon-2026-05-18.md`: changes only `receiveShadow`, not visibility — per the audit agent's read this is not the cause, but should be confirmed if the gate hypothesis falls.

## 7. Wave 1 findings (2026-05-20)

Three imperative probes ran today. Their outputs reshape the brief.

### 7.1 Bug A: bilinear blend is the wrong model, by ~10× (CONFIRMED)

**Numeric simulation** (`/mnt/wbterminal1/tmp/claude-scratch/ground-fidelity-2026-05-20/bilinear_sim.js`) of the formula at `terrain.js:520-530` against synthetic 9×9 road grids:

| Test pattern | Effective road width | Retail target |
|---|---|---|
| Straight row (j=4 all road) | **47.9 m** | 5.0 m |
| Diagonal (i == j) | **65.7 m** | 5.0 m |
| Single isolated vertex (4,4) | **32.85 m radius** | ~2.5 m radius |

The `> 0.001` threshold at `terrain.js:526` barely clips the linear ramp — any cell with even one road-flagged corner paints essentially the entire cell as road.

**Retail trace** (`acclient.c`): retail does NOT compute road geometry from `_road_width = 5.0` at render. It uses **precomputed `RoadAlphaMap` textures** indexed by `rcode`. The lookup at `acclient.c:304697 (TexMerge::FindRoadAlpha)` returns a per-rcode alpha texture whose shape is baked into the DAT. The 5.0 m constant is only read by `LandDefs::get_vars` for serialization (`acclient.c:299510`), never at draw time. So the bilinear-vs-discrete framing in §2.3 is incomplete — the right model is "precomputed alpha texture per direction code", and the discrete-mask prototype is an approximation.

**Single active code path** (grep verified): no competing road-mesh / overlay-quad path in `emit-dynamic-site`. The "overlay mesh" language in `docs/visual-fidelity-handoff-pk-2026-05-13.md:103-104, 151` is stale doc — the mesh was removed when roads moved into the terrain shader. `terrain.js:18-21` carries an outdated comment claiming "Roads are rendered as a thin triangle-strip overlay mesh" which contradicts the actual code; clean that up.

### 7.3 Bug A fix is one line — threshold change, not discrete-corner gate

A second pass of `bilinear_sim.js` compared the discrete corner-count formula against the bilinear-blend approach with a sharper threshold. The discrete approach was wrong; the threshold tweak is right.

| Formula | A width | B width | C radius | Verdict |
|---|---|---|---|---|
| `bilinear > 0.001` (current) | 47.9 m | 65.7 m | 32.85 m | baseline |
| discrete corner N≥2 | 47.9 m | 0 m | 0 m | paints whole cells; misses diagonals/isolated |
| discrete corner N≥3 | 0 m | 0 m | 0 m | never triggers |
| discrete corner N≥4 | 0 m | 0 m | 0 m | never triggers |
| `bilinear > 0.5` | 23.9 m | 19.8 m | 11.95 m | still 4× retail |
| `bilinear > 0.8` | 9.6 m | 7.1 m | 4.8 m | close |
| **`bilinear > 0.9`** | **4.7 m** | **3.4 m** | **2.35 m** | **matches retail (5 / 5 / ~2.5)** |
| `bilinear > 0.95` | 2.3 m | 1.7 m | 1.15 m | too narrow |

**Proposed fix.** In `external/holtburger/apps/holtburger-web/scene3d/terrain.js:526`, change the gate threshold from `0.001` to `0.9`. The bilinear value is still used as the mix weight inside the gate, which keeps the colour ramp continuous on the narrow road band. For antialiasing, replace the hard `if (roadMask > 0.9)` with `smoothstep(0.85, 0.95, roadMask)` so a ~1 m feather covers the road edge.

The original GROUND-A.2 plan (corner-count discrete mask behind `?road=discrete`) is **superseded** — the numeric simulation shows it cannot match retail's 5 m width for diagonal or isolated road patterns.

`fetch_landblock_spawns_soa` at `apps/holtburger-web/src/lib.rs:2299` was doing a serial `for &cell_id in &cell_ids { fetch_one_lb(...).await }` — 169 sequential HTTP round-trips on the validator ring. May 16 timing: 2,281,904 ms (38 min). Replaced with `futures::future::join_all` over the same set of futures (lib.rs:2310-2334); `cargo check --target wasm32-unknown-unknown -p holtburger-web` passes clean. Rebuilt `pkg/` via `wasm-pack build --target web --out-dir pkg --release` (2m 01s).

| Stage | May 16 | Today | Speedup |
|---|---|---|---|
| `fetch_landblock_spawns_soa` | 2,281,904 ms (38 min) | **37,976 ms (38 sec)** | **60×** |
| Stage 3 elapsed | 2,281,921 ms | 37,998 ms | 60× |
| Full validator run | ~40 min | **~3 min** | 13× |

Same serial pattern exists in `fetch_landblock_scenery_soa` (lib.rs:2189-2204), but scenery's cache is pre-warmed by init3D so cold-cache calls are rare. Left untouched as scope.

**Also caught:** the GROUND-B.1 command in §3.4 was `--ring 0xA9B4`. The validator's regex requires `0xMINLB..0xMAXLB`; the single hex exits 2 at parse time. Omit `--ring` (default `0xA3AE..0xAFBA` is correct) or pass the full range. Already noted in §7.2.
