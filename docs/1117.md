## 2. Landed: client-side urgent-first dispatch queue (JS-only, wasm untouched)

`bake_worker_client.js` — requests now dispatch through three lanes with
an in-flight cap (default 4, `?bakeQueueCap=N`):

- **lane 0** — `init` + urgent-tagged surface/mesh fetches (the same
  `isNearPlayerLb` signal that rides `msg.urgent` to the worker wasm's
  fetch-semaphore bypass; server-LB stamped since s8);
- **lane 1** — normal surface/mesh;
- **lane 2** — the entity-surface types + diagnostics. Entity surfaces
  carry NO urgency signal at any layer (the wasm ABI has no urgent arg on
  `fetchEntitySurfacesPixels`/`…Batch`), so they can only be demoted, not
  promoted — a dyed NPC on the current LB cannot be made urgent without a
  wasm signature change (owed, §4).

`_pump()` drains lane 0 fully before lane 1 before lane 2, FIFO within a
lane; replies free slots and re-pump; `_failAll` drains the lanes too
(queued entries reject with the posted ones) so a worker respawn starts
clean. The queue sits UPSTREAM of the per-request main-thread fallback,
so the fallback path is covered for free. `?bakeQueue=off` (0/false)
restores post-immediately — the s8 arm, for A/B. Observability:
`bakeWorkerStats().queue` = {enabled, cap, queuedNow, inFlightPosted,
posted, maxQueuedLen, byLane[{count, avgQueueMs, maxQueueMs}]}.

⚠ Semantics change for cross-session comparisons: `_pending` (and thus
`pendingNow`/`maxPending`/`avgDepth`) now counts queued-not-yet-posted
requests too — s9-POST depth numbers are NOT comparable to s8/s9-PRE.
Queue-lane waits are the new first-class signal.
