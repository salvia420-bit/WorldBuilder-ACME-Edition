# PHY-07 live run — 2026-07-26

Purpose: settle whether static scenery (trees/rocks) and doors block the local
player, after the user reported that in the live client you can run straight
through all of them. Method was to be a headless `?nullRender=1` walk against
local ACE, reading the client's own placement data.

**Outcome: the collision question is still OPEN.** The harness works and produced
real measurements, but the client wedges before the player can be manoeuvred
adjacent to a tree. Three *new* defects were found along the way, and they are
arguably more actionable than the original question.

## Coordinate mapping (derived and confirmed against two independent poses)

```
three.js X =   ((lb >>> 24) & 0xff) * 192 + pose.x
three.js Z = -((((lb >>> 16) & 0xff))    * 192 + pose.y)
three.js Y =   pose.z
```
Confirmed by comparing the follow-cam world position against the pose at two
separate locations (agreement within the cam's trailing offset, ~6 m). This is
worth keeping — it makes any render-space assertion testable against wasm pose.

## What was measured

**Movement works and is unobstructed over long distances.** Three valid straight-
line walks through Holtburg town:

| Run | Distance | Landblocks crossed |
|---|---|---|
| baseline-forward (4 s hold) | 74.15 m | `a9b40019` → `a9b4001c` |
| mobility-recheck (2.5 s hold) | 44.38 m | crossed |
| post-recovery (2 s hold) | 34.80 m | crossed |

None of the three stopped or deflected. Crossing a town centre for 74 m without
a single block is consistent with the user's report, but is not proof on its own
— the paths were not verified to intersect a specific obstacle.

**Closest approach to a static was 8.85 m.** The one valid sweep run measured
minimum distance from the player to any `source:'statics'` placement centre
(9-landblock neighbourhood, elevation-filtered) at every 300 ms sample. It never
got closer than 8.85 m, so it cannot decide the question. Subsequent sweep runs
were invalid (see wedge below).

**Placement data is available and rich** — `window.__diag.placements.walk(lbHigh)`
returns per-instance rows `{source, modelId, position:[gx,gy,gz], rotation, scale}`,
453-455 rows for landblock `a9b4`. This is the right oracle for a future attempt;
`source` distinguishes `statics` / `entities`.

## Three new defects found

### LIVE-01 — `@teleloc` with an outdoor cell silently lands the player in an interior cell and wedges them
`@teleloc 0xA9B4001C 129.6 11.9 95.5` (a legal outdoor cell, `0x1C` = 28, within
the outdoor range 1..64) came back as pose landblock **`a9b4013f`** — cell
`0x13F` = 319, far outside the outdoor range, i.e. an env-cell/building interior.
The player was then **completely immobile**: a 3 s forward hold produced
`planarDist: 0` with the pose bit-identical before and after
(`129.599609375, 11.8984375, 95.50499725341797`). Recovery required `@telepoi`.
Whether ACE or the client picks the cell needs checking, but from the client's
side this is an unrecoverable-by-input wedge.

### LIVE-02 — the player ends up ~26 m below the starting surface, immobile, after ordinary walking
After the sweep walks the pose was `a9b40026 (109.13, 129.97, z=66.83)`, having
started the sequence around z=92-95, and forward input produced zero displacement
across five consecutive 10 s runs (minimum distance to the nearest static frozen
at 16.99 m — so *not* pressed against a static). Physics was healthy throughout:
`__diag.physics.summary()` reported 600 samples over 19.77 s (≈30 Hz),
`drift {max:0, avg:0, p99:0}`, `hitchCount: 0`, `lastSampleAgeMs: 9.3`. So the
integrator is running and reporting no drift while the player cannot move —
a wedge the existing diag surface does not detect.

### LIVE-03 — degenerate follow-camera basis
At the wedged position the camera's world matrix had horizontal forward
components **exactly (0, 0)** (`-m[8] = 0`, `-m[10] = 0`), i.e. the camera basis
is looking straight down/up with no yaw component. Any consumer normalising that
vector divides by zero. This silently poisoned this run's turn loop (see below)
and would poison any heading-derived logic.

## Harness lesson — the rig produced its own false positive

`collide.cjs` first reported `verdict: "BLOCKED (plateau)"`. It was wrong: the
distance-to-target series was flat because **the player never moved at all**, not
because something stopped them. The turn loop had also silently failed —
`turnErrSeq` was the identical value `-123.9` for all 24 iterations, because
heading came from the degenerate camera basis of LIVE-03.

Both faults were caught by adding sanity gates, now in `sweep.cjs`: a run is
`valid: false` unless total displacement > 2 m, and the interpretation string
reports `INVALID — player never moved` rather than a verdict. **Any future
collision assertion must gate on "did the player actually move" and "did the
heading actually change" before it is allowed to conclude anything.** This is the
same class of error as the agent findings this log exists to catch, produced by
the orchestrator's own instrument within minutes of writing it.

## Quantitative anomaly worth a separate look

Walk speed measures ≈13-18 m/s (74.15 m in a 4 s hold plus ~0.8 s settle;
44.38 m in 2.5 s). Retail run is ~4 m/s and holtburger's own cap is documented as
4.5 m/s. That is 3-4× too fast. Possible confounds not excluded: buffs on this
character, a prior `/godly`, or pose units. It is independent support for agent
A's **OQ-3** (our walk base 2.602 vs `get_state_velocity` 3.1199999) being a real
divergence, and it means every distance-based timing in the sweep was covering
ground 3-4× faster than a retail client would.

## What a next attempt should do differently

1. **Do not teleport next to obstacles** — LIVE-01 makes `@teleloc` unsafe for
   fine positioning. Use `@telepoi` for the coarse move and walk in from there.
2. **Fix heading acquisition** — read yaw from the player's own pose/quaternion
   (wasm) rather than the follow-cam, so LIVE-03 cannot poison it.
3. **Pick the target first, then approach** — choose a `statics` placement from
   `__diag.placements.walk()` within 10-15 m, and verify approach by watching
   min-distance strictly decrease; abort the run the moment displacement stalls.
4. **Reach the wasm collision exports.** `populateStaticsAabbsForLandblock`,
   `holtburg_static_object_count`, `holtburg_test_collision_clamp_axis_aligned`
   and `holtburg_test_collision_slide_along_wall` all exist in
   `pkg/holtburger_web.d.ts` but are **not reachable from `window`** (module
   scope only; `window.__hbWasm` exposes 27 keys, none of them collision).
   Exposing them behind a diag flag would answer "is the AABB/BSP index populated
   for this landblock" directly, without any walking at all — that is the cheap
   decisive instrument and should be built before the next attempt.
5. Consider driving the two `holtburg_test_collision_*` self-tests first — if
   those pass in the live build, the clamp maths is fine and the fault is
   residency/wiring, which is exactly the fork this run set out to resolve.
