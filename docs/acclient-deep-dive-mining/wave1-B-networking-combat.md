**Architectural fact that governs every disposition below:** holtburger is *not* a thin
wrapper around a proxy. `crates/holtburger-session` is a full re-implementation of the AC
UDP session — 20-byte header, `0xBADD70DD` checksum, ISAAC-keyed checksum encryption,
packet sequencing, retransmit request/serve, 16-byte fragment headers, reassembly. The
WebSocket bridge (`apps/holtburger-wsbridge`) only adds a 2-byte big-endian port prefix
and relays datagrams verbatim (`crates/holtburger-transport-ws/src/frame.rs:20-50`).
So retail transport mechanics are **in scope**, not N/A — the only genuinely moot items are
those that depend on a real socket/OS (ICMP, recv-buffer sizing, multi-homing) or on a
retail login/world-server split that this ACE build never exercises.

## PART 2 — TASKS

### Networking

#### NET-01 — Optional-header cursor is missing 7 wire flags; any packet carrying one is silently dropped
- **Source §:** `02-networking.md` §2 "Optional headers" (the 20-row mask table).
- **Retail:** the optional-header block is a strictly mask-ascending chain. Sizes/identities from the `COptionalHeaderAllocatorTemplate<MASK, T>` instantiations: `0x100` ServerSwitch (`CServerSwitchStruct`), `0x200` LogonServerAddr (`sockaddr_in`), `0x400` empty (`CEmptyHeader<1024,7>`, never sent), `0x800` **Referral** (`CReferralStruct`), `0x1000` NAK list (`m_IDs[115]`), `0x2000` EmptyAck list, `0x4000` PAK, `0x8000` empty (`CEmptyHeader<32768,3>`, never sent), `0x10000` Logon, `0x20000` WorldLoginRequest (`u64` cookie), `0x40000` ConnectRequest (`CConnectHeader`), `0x80000` ConnectResponse (`u64`), `0x100000` NetError, `0x200000` NetError-Disconnect, `0x400000` ICMD (`{Cmd, Param}`), `0x1000000` TimeSync (`long double`), `0x2000000`/`0x4000000` Echo, `0x8000000` Flow (`CFlowStruct`).
- **holtburger today:** `crates/holtburger-session/src/optional_header.rs:59-141` walks only `SERVER_SWITCH, REQUEST_RETRANSMIT, REJECT_RETRANSMIT, ACK_SEQUENCE, CONNECT_REQUEST, LOGIN_REQUEST, CONNECT_RESPONSE, CICMD, TIME_SYNC, ECHO_REQUEST, ECHO_RESPONSE, FLOW`. **ABSENT:** `0x200`, `0x400`, `0x800`, `0x8000`, `0x20000` (the constant exists at `crates/holtburger-protocol/src/messages/transport.rs:43` but has no cursor arm), `0x100000`, `0x200000`. Because `hash_bytes()` (`optional_header.rs:34-43`) feeds the payload checksum, an unrecognised header shifts every subsequent offset → `validate_received_packet_checksum` fails (`crates/holtburger-session/src/session/receive.rs:198-209`) → the packet is dropped with only a `log::debug!`.
- **Proposed change:** add the missing arms with correct sizes, mask-ascending. `0x400`/`0x8000` are zero-length (safe no-ops that keep the chain aligned). Add a `#[test]` that walks a synthetic packet with every flag set and asserts `payload_offset()` equals the hand-computed total.
- **Payoff:** removes a whole class of silent, undiagnosable packet loss. ACE *does* have a `Referral` sender (`Network/Packets/PacketOutboundReferral.cs:7` sets `EncryptedChecksum | Referral`) — dormant in this build, live the moment anyone enables a world-server split or points holtburger at a different ACE fork.
- **Bridge note:** the bridge is the right place for nothing here — it relays bytes; the fix belongs in the session.
- **Effort:** S.
- **Validation:** unit test on the synthetic all-flags packet; then a live-ACE packet capture (`Session::set_capture`, `crates/holtburger-session/src/capture.rs`) replayed through the cursor asserting zero checksum-drop lines in the log.

#### NET-02 — `DISCONNECT = 0x8000` is an inherited ACE mislabel, and neither disconnect signal is handled
- **Source §:** §2 optional-header table (rows `0x8000` and `0x200000`) + §7 "Timeouts and auto-reconnect".
- **Retail:** `0x8000` is an unnamed payload-less header that appears only in its two `CreateFromStream` bodies (acclient.c:468686, 468710) and its registration (801015-801016) — **never sent, never handled**. The doc says explicitly: "Earlier drafts named `0x8000` 'Disconnect'; that name is not supported by anything in the binary." The real wire disconnect is `0x200000` NetError-Disconnect, handled at acclient.c:370725 and 372714, which drives `SetConnectionState(cs_DisconnectReceived)`.
- **holtburger today:** `crates/holtburger-protocol/src/messages/transport.rs:41` — `pub const DISCONNECT: u32 = 0x00008000;` (ACE's `PacketHeaderFlags.cs:19` comment is literally `Disconnect = 0x00008000, // Empty Header 2`). The constant has **zero readers**; `0x100000`/`0x200000` are not defined at all. A server-initiated disconnect is therefore invisible — holtburger learns about it only from the 90 s staleness timer (NET-11).
- **Proposed change:** (a) rename `DISCONNECT` → `EMPTY_HEADER_2` with a comment citing the doc, and keep an `#[deprecated]` alias so nothing breaks; (b) add `NET_ERROR = 0x00100000` and `NET_ERROR_DISCONNECT = 0x00200000`, both with cursor arms (NET-01) and a receive arm that surfaces `CLIENT_EVENT_KIND_DISCONNECTED` with the decoded `NetError` reason instead of a generic timeout string.
- **Payoff:** correct, immediate, *attributed* disconnect UX ("booted", "account in use", "speedhack") instead of a 90 s hang. Also removes a name that will mislead the next reader.
- **Effort:** S.
- **Validation:** ACE terminates a session with `SessionTerminationReason` — trigger a duplicate login (the `autoLogin` kick-dance already does this, `index.html:10004`) and assert the disconnect event carries a reason within one RTT rather than at T+90 s.

#### NET-03 — No clean logoff: page teardown leaves an in-world ghost for up to 60 s
- **Source §:** §5 `Proto_UI` direct sends (`0xF653` LogOffCharacter on queue 4); §7 `logOffSent_` gating the referral auto-reconnect; §2 `0x200000` as the wire disconnect.
- **Retail:** the client sends `0xF653 LogOffCharacter` and sets `logOffSent_`, which suppresses the referral-based auto-reconnect. A deliberate teardown also emits a `0x200000` NetError-Disconnect header.
- **holtburger today:** `apps/holtburger-web/index.html:5381-5388` — `pagehide` calls `handle.free()` and nulls `window.__sessionHandle`. It does **not** send `CharacterLogOff`. The message *exists* (`crates/holtburger-protocol/src/opcodes.rs:351`, pack at `messages/game_message/pack.rs:76-78`) and the native CLI does send it (`crates/holtburger-core/src/client/commands.rs:949`) — the browser path does not.
- **Proposed change:** in the `pagehide`/`beforeunload` handler, call a new synchronous `SessionHandle.logOffNow()` that packs `GameMessage::CharacterLogOff` (+ optionally a bare `NET_ERROR_DISCONNECT` header packet) and pushes it straight through the transport before `free()`. Must be fire-and-forget synchronous — an `async` send will not complete during unload. In `?netWorker=1` mode post a `TX_KIND_MESSAGE` and let the worker flush.
- **Payoff:** kills the "character already in world" login failure loop (`CharacterError::EnterGameCharacterInWorld = 0x0D`, documented at `apps/holtburger-web/src/lib.rs:21826-21833`) that currently forces the ~5.5 s retry dance on every reload.
- **Effort:** S.
- **Validation:** headless bot: login, `?autoSpawn=first`, navigate away, immediately re-login; assert no `CHARACTER_ERROR` kind=20 event and no 5.5 s retry. Cross-check ACE's log for a clean `LogOffPlayer` instead of a timeout reap.

#### NET-04 — Optional-header chain places `CONNECT_REQUEST` (0x40000) before `LOGIN_REQUEST` (0x10000)
- **Source §:** §2 optional-header mask table (ascending mask order is the wire contract).
- **Retail:** headers are emitted/parsed in ascending mask order: `… 0x4000 PAK, 0x8000, 0x10000 Logon, 0x20000 WorldLoginRequest, 0x40000 ConnectRequest, 0x80000 ConnectResponse …`.
- **holtburger today:** `crates/holtburger-session/src/optional_header.rs:104-123` — step 5 is `CONNECT_REQUEST` (32 B), step 6 is `LOGIN_REQUEST` (rest-of-packet), step 7 is `CONNECT_RESPONSE`. ACE's own inbound parser (`Network/PacketHeaderOptional.cs`) has `LoginRequest` → `WorldLoginRequest` → `ConnectResponse` and no `ConnectRequest` arm at all (it's server→client only).
- **Proposed change:** reorder to `… ACK_SEQUENCE, LOGIN_REQUEST, WORLD_LOGIN_REQUEST, CONNECT_REQUEST, CONNECT_RESPONSE, NET_ERROR, NET_ERROR_DISCONNECT, CICMD, …`. Note `LOGIN_REQUEST`'s "rest of packet" sizing means it must be **last** among headers that co-occur with it — retail gets away with mask order because nothing after `0x10000` ever accompanies a logon packet. Encode that invariant as a debug assertion rather than relying on luck.
- **Payoff:** latent-bug removal; today no ACE packet sets both bits, so this is dormant. Do it while touching the file for NET-01.
- **Effort:** S.
- **Validation:** the same synthetic all-flags unit test as NET-01, plus one asserting a logon packet's `payload_offset()` is unchanged.

#### NET-05 — Client never sends `EchoRequest`, so there is no RTT and ACE's own latency check never runs
- **Source §:** §2 optional headers (`0x2000000` EchoRequest / `0x4000000` EchoResponse); §7 "state 5 … snapshots `CLinkStatusSnapshot`, feeds `CLinkStatusAverages`"; §10 (the client-side time check).
- **Retail:** the client emits `0x2000000` EchoRequest headers; the server answers `0x4000000`; the round trip feeds `CLinkStatusSnapshot`/`CLinkStatusAverages`, which is what the 4 s / delay > 40.0 watchdog in `CPlayerSystem` (acclient.c:400555-400562) reads.
- **holtburger today:** `ECHO_REQUEST_SIZE = 4` / `ECHO_RESPONSE_SIZE = 8` exist (`transport.rs:26-27`) and the cursor handles both, but **nothing ever sends an EchoRequest** (grep for `ECHO_REQUEST` outside `optional_header.rs` and the flag definition returns only the reply arm). The only echo code is a *response* to a server EchoRequest at `crates/holtburger-session/src/session/receive.rs:244-248` — which is dead against ACE (ACE only ever sets `EchoResponse` outbound, `NetworkSession.cs:943-944`). That reply also has two defects: it sends an **empty payload** where ACE writes two floats, and it reuses the **server's** `header.sequence` on a client→server packet (`resp = packet.header.clone()` keeps `sequence`).
- **Proposed change:** (a) add `Session::send_echo_request()` writing the client time as an `f32` and record the send instant; (b) on an inbound `ECHO_RESPONSE`, compute RTT and expose it (NET-19); (c) fix the response arm to write the 8-byte payload and to use `current_client_sequence()`; (d) send an EchoRequest on the keepalive tick (NET-07) so keepalive and RTT are the same packet.
- **Payoff:** first-ever RTT/jitter measurement in the browser client; unblocks NET-11's link-delay arm; also enables ACE's `VerifyEcho` diagnostics (`NetworkSession.cs:600-650`) which currently never fire because they are driven purely by client EchoRequests.
- **Effort:** M.
- **Validation:** packet capture against live ACE showing EchoRequest/EchoResponse pairs; assert `__diag.net.rttMs` is finite and within 2× of `ping` to the ACE host.

#### NET-06 — `TimeSync` is received and thrown away: no server clock, no speedhack latch
- **Source §:** §10 "Anti-tamper" (`ClientNet::HandleTimeSynch` sets local time from the server; if `srvtime + 60 < cur_time` holds continuously for 60 s the client self-reports `ID_ConnectionError_RunningSpeedhack` via a `0x100000` NetError; any in-tolerance sync resets the latch); §2 optional header `0x1000000` = `long double`.
- **Retail:** the client both **consumes** server TimeSync (setting `Timer::local_time`) and **sends** its own — ACE's own comment records the observed cadence: "Server seems to send them every 20 seconds per port. Client seems to send them alternatingly every 2 or 4 seconds per port" (`NetworkSession.cs:619-624`).
- **holtburger today:** inbound TimeSync is parsed into `SessionEvent::TimeSync(f64)` at `crates/holtburger-session/src/session/receive.rs:432-439` — and then discarded in **both** loops: `apps/holtburger-web/src/net_worker.rs:359-363` ("TimeSync is dropped (the main recv loop ignores it too)"). Outbound TimeSync: ABSENT. There is therefore no server-authoritative clock anywhere in the client; every timestamp-bearing wire field (`Enchantment::start_time`, `PlayerEnchantment.start_time`) is interpreted against a locally-derived Derethian epoch (`plugins/buffs-hud.js` remaining-time math).
- **Proposed change:** (a) keep a `server_time_offset: f64` on `Session`, updated from every inbound TimeSync and from the `ConnectRequest.time` field (already parsed, `transport.rs:71-72`); (b) expose `serverTime()` to JS and make buff-remaining and `last_time_degraded` math use it; (c) send a TimeSync header on the keepalive tick. Do **not** port the self-reported speedhack NetError — it is a client-side accusation of its own user and ACE already has an independent echo-based check.
- **Payoff:** buff/debuff timers stop drifting when the tab is throttled or the local clock is off; fixes a whole class of "buff shows 12 s left forever" reports. Also the correct base for any future degrade math (CMB-18).
- **Effort:** M.
- **Validation:** headless bot with the system clock deliberately skewed ±5 min; assert buff remaining-time matches ACE's `@enchantments` output. `__diag` surface for `serverTimeOffsetSec`.

#### NET-07 — Keepalive is a full `GameAction PingRequest`, not a bare control packet
- **Source §:** §7 "state 5 — every 2.0 s, snapshots `CLinkStatusSnapshot` … and fires `NotifyPluginsOfHeartbeat`"; §2 `EnqueuePak` ≥ 2.0 s.
- **Retail:** the heartbeat is a **transport-level** event: an empty packet carrying PAK/NAK optional headers on a 2.0 s cadence, plus the client's own 2/4 s TimeSync. It consumes no blob, no fragment sequence, no UI counter, and provokes no server-side game logic.
- **holtburger today:** `apps/holtburger-web/src/net_worker.rs:350` (`IntervalStream::new(2_500)`) → `:377-385` sends `GameAction::PingRequest`. The main-thread path does the same on a 5 s interval (`apps/holtburger-web/src/lib.rs:45076-45111` arm). Each ping burns a `game_action_sequence`, a `fragment_sequence`, a `fragment_id`, a full 16-byte fragment header and an ISAAC key, and ACE answers with a `PingResponse` GameEvent (`opcodes.rs`: `PingResponse = 0x01EA`) that has to be unpacked and discarded — ~24 pointless round trips per minute per client.
- **Proposed change:** replace the keepalive payload with a bare cleartext control packet carrying `ACK_SEQUENCE | TIME_SYNC | ECHO_REQUEST` (which lands NET-05 and NET-06 for free). `queue_deferred_cleartext_control_packet` (`crates/holtburger-session/src/session/send.rs:153-179`) already does exactly this shape for ACKs. Move the cadence to 2.0 s to match retail. Keep `PingRequest` as an explicit `/ping` slash command only.
- **Payoff:** removes the single largest source of non-retail C2S traffic; stops advancing the game-action sequence during idle (which currently makes `game_action_sequence` a useless diagnostic); reduces ACE inbound-dispatch work.
- **Effort:** S.
- **Validation:** capture 60 s idle in-world; assert zero `GameAction` frames and ≥ 25 control packets; assert ACE's session stays alive past 5 min (`__diag`/`__bootState` remains `in-world`).

#### NET-08 — `LoginRequest` is sent exactly once; a single lost datagram hangs login forever

## PART 3 — OPEN QUESTIONS

**Q1 — Does ACE ever send two enchantments sharing their low 16 bits?** CMB-13's whole weight rests on this. Retail's `AttemptToReplaceSpellInList` treats low-16 collisions as the same enchantment; holtburger treats them as distinct. If ACE never produces such a pair the divergence is harmless; if it does, buffs silently double-count into armour and resistance. Answer by dumping `playerEnchantments()` grouped by `spell_id & 0xFFFF` after a long self-buff session. The doc also warns that the related ≥ `0x8000` "layered/set spells" reading is **unverified**, so do not use that range as evidence either way.

**Q2 — Which retail behaviour does the `Indicator` stamp comparison actually implement?** §3 is explicit that acclient.c:378070 reads `if (!LHSNewerOrderingStamp(stored, incoming)) return;` — so the half-assembled blob is replaced when the **stored** blob is newer and the function **returns** when the incoming stamp is newer, the opposite of the intuitive behaviour — and that this reading is stable across all three decompilations with argument-order-coherent neighbours. The doc concludes it is probably a genuine latent inversion in Turbine's code. NET-14(b)/NET-15 therefore cannot simply "port §3": someone has to decide whether holtburger should reproduce the inversion (bug-compatible) or implement the intent. Recommendation: implement the intent, and comment the divergence with the citation.

**Q3 — Is the bits-48-55 "server ID" field in `blobID` real?** §3 labels it inference: "`MakeInitialSequenceID` (467831) and `MakeNetBlobID` (467837) both decompile degenerately and do **not** independently establish it." NET-15's `BlobId` newtype should expose it as `raw_bits_48_55()` with a comment rather than a confident `server_id()` accessor.

**Q4 — Are `0xF7E8` / `0xF7E9` really `DDD_BeginPullDDDMessage` / `DDD_IterationDataMessage`?** §9: "`0xF7E8` and `0xF7E9` have no constant anywhere. Two orphan PDB types … are the only unassigned candidates, but the binary does not prove the association." holtburger asserts the mapping (`crates/holtburger-protocol/src/opcodes.rs`: `DddBeginPullDdd = 0xF7E8`, `DddIterationData = 0xF7E9`), inherited from chorizite/ACE. Not wrong — unproven. Worth a source comment; resolvable only from a real DDD capture.

**Q5 — How much of §6's motion-style table is build-specific?** CMB-11 establishes that `AtlatlCombat`/`ThrownShieldCombat` differ by exactly 3 between the 2013 binary (`0x138`/`0x139`) and the shipped end-of-life DATs + ACE (`0x13b`/`0x13c`), because the ID's low 16 bits are the `command_strings` array index and three commands were inserted ahead of index 312 in a later patch. The `0x3C`-`0x49` block is stable. **Which other high-index constants in the pack are similarly era-shifted?** Any deep-dive constant whose low bits equal an array index — motion commands, the `command_ids_1` range generally — needs an era check before being treated as authoritative against the DATs we bake from. This is a caveat that belongs in the pack's README, not just here.

**Q6 — Is holtburger's client-side swing prediction a feature or a divergence to unwind?** §1 is unambiguous that retail's client does not derive a swing motion from `(style, height, attack_type)` — the CMT's contents are dead and the animation arrives from the server. holtburger has built a full CMT pipeline that (a) contradicts that finding and (b) misses its stance lookup 100 % of the time under default flags (`apps/holtburger-web/ui/ac_combat_maneuver.js:28-47`). Someone with authority over the client's latency-hiding strategy needs to pick: retail-faithful (server-authoritative swings, CMT for prediction-with-reconcile only) or explicitly-divergent (flip `?cmtStanceMask` on and document why). CMB-06 is blocked on this answer.

**Q7 — Does the DAT's `SkillFormula` record carry `w`, `x`, `y`?** CMB-21 assumes it must, since retail reads all four coefficients. If holtburger's parser is discarding them the fix is in the DAT layer, not the math; if every shipped record has `w=0, x=y=1` then holtburger's simplification is exactly right and CMB-21 closes as PARITY-OK. Cheap to settle with one WBT dump.

**Q8 — Which property is retail's unconditional `InqSkill` enlightenment term, and is holtburger adding it twice?** `0x16D` = 365 = holtburger's `LumAugAllSkills`; holtburger separately has `Enlightenment = 390` with a `training >= Trained` gate. If both are summed (`crates/holtburger-core/src/client/skill_info.rs:194-206`), enlightened characters have inflated skills. ACE's `Skill.cs` is the arbiter. See CMB-22.

**Q9 — Should the wsbridge grow a control plane?** Several retail transport behaviours are expressible only if the bridge can change its upstream: referral to a different host (NET-01/NET-26), and any future world-server split. Today the WS URL pins one host and port range. The alternative — reject referrals loudly — is cheaper and honest, and is what NET-26 recommends for now. But if holtburger is ever pointed at a multi-server ACE fork, this becomes load-bearing.

**Q10 — What is the intended source of truth for the 2/4 s client TimeSync cadence?** ACE's own comment (`NetworkSession.cs:619-624`) records the observed retail client sending TimeSync "alternatingly every 2 or 4 seconds per port", but §10 documents only the *receive* side (`HandleTimeSynch`) and does not describe a client send site. Before NET-06 adds outbound TimeSync, someone should find the retail send site (or confirm the alternation is really EchoRequest being misremembered) so the cadence is grounded rather than copied from a comment.
